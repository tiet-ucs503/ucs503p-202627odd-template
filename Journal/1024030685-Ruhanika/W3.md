# W3 — Dataset Collection & Project Refinement

## Objective

To move from a conceptual prototype towards a more realistic and data-driven system by collecting local business data for Patiala and identifying the changes required in the existing CityServe application.

## Work Done

During Week 3, we focused on improving the realism of CityServe by working on the actual vendor/service dataset.

Since CityServe is intended to connect users with local service providers, we realised that using only fictional or manually created vendors would make the prototype less convincing. Therefore, we started collecting local business information for Patiala and organized the collected data into a structured CSV dataset.

The dataset included information such as:

- Business name
- Category
- Subcategory
- Address
- Locality/area
- City
- Contact information
- Website, where available
- Latitude and longitude
- Ratings
- Review count
- Source information
- Place ID, where available

The collected data covered different types of local services such as electricians, plumbers, repair services, salons, mechanics, laundry services, tailors and other local businesses.

## Dataset Structuring

After collecting the information, we cleaned and organized it into a CSV format so that it could later be imported into the application's database instead of manually entering each vendor.

We also started thinking about how the dataset fields would map to the existing CityServe database structure.

For example:

```text
Business Name
      ↓
Partner

Category
      ↓
Category / Subcategory

Location
      ↓
Latitude + Longitude + Address

Rating
      ↓
Partner Rating
```
This helped us understand that the dataset should not simply be displayed on the frontend as static information. It should become part of the actual application workflow.

## Changes and Improvements Identified

While working with the dataset, we also identified several areas of the existing prototype that needed improvement.

We realised that:

- The UI contained more information and sections than necessary.
- Some tables and components were not adding enough value to the user experience.
- The service categories needed to better match the actual local dataset.
- Vendor information needed to come from the database rather than only from hard-coded data.
- Location information should be meaningful for nearby service discovery.
- The distinction between a sourced local business and a CityServe-verified partner needed to be maintained.

We therefore planned to simplify the interface and make the data flow more realistic.

## Key Learning

The main learning from Week 3 was that collecting a dataset is not enough. The data needs to be structured in a way that can actually support the application's functionality.

We also understood that the quality of the dataset directly affects the credibility of the marketplace. This shifted our focus from building only a visually appealing prototype towards building a more realistic and data-driven system.
